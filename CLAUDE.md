# CLAUDE.md: instructions for Claude Code

You are implementing a **dbt + DuckDB analytics project for a remittance fintech (Félix Pago)**.
It is a take-home assessment for a **Data Engineering Manager** role, so quality, clarity and engineering
standards matter as much as correctness. Reviewers will clone the repo and run it on their own machine.

## Read these first (sources of truth, in order)
1. `docs/ASSIGNMENT.md`: the original brief. Never contradict it (e.g. **no dbt seeds**).
2. `docs/DESIGN.md`: the full architecture (v7), including the decision records (§18). **Follow it.** If you think something in it is wrong, stop and say so instead of quietly diverging.
3. `docs/IMPLEMENTATION_PLAN.md`: the step-by-step phases with tasks and acceptance checks. **Work one phase at a time** and tick the checkboxes as you go.

## Non-negotiable rules
1. **No dbt seeds. Ever.** There is no `seeds/` folder. Source CSVs are loaded by `src/load_raw.py` into the `raw` schema. Small reference data lives in `vars` and goes through the `values_from_var` macro.
2. **Never modify `data/source/` or `data/test_batches/`.** Only `data/landing/` is a working copy (git-ignored, recreated by `python run.py reset-data`).
3. **Facts store ingredients, not recipes.** Fact tables contain only additive measures (amounts, 0/1 flags, counts) and slicing columns. **No** `*_rate`, `*_pct`, `avg_*`, `*_ratio`, medians, distinct counts, MoM/YoY or ARPU in any table. Those are **MetricFlow metrics** in `dbt/models/semantic/`. Classification labels the brief asks for (`volume_segment`, `is_recurring` / `lifecycle_status`, `reliability_tier`, `cluster_type`) are allowed as **dimension attributes**. The custom test `no_derived_metrics_in_facts` enforces this.
4. **Every model has YAML** in its folder's `_<folder>__models.yml`: a model description, **every column** with `description` and `data_type`, tests, and `meta` (owner and grain for marts, `additivity` for fact measures, `pii: true` where relevant). Reuse definitions with `{% docs %}` blocks from `dbt/models/docs/_glossary.md`.
5. **Kimball:** marts are folders `core/` (conformed dims), `finance/`, `operations/`, `growth/`, `risk/`. Facts declare their grain. SCD2 dims come from **snapshots**. Every dim has an **unknown member** row. Facts point to dims through surrogate keys, using point-in-time joins for SCD2.
6. **Use the macros** for repeated logic (cleaning, dedupe, PIT join, unknown member, FX revenue). Don't copy-paste SQL patterns.
7. **Runs anywhere with Python only.** `run.py` is the single entry point (no Make, no Docker). No absolute paths, and no reliance on `~/.dbt`.
8. **Don't invent requirements.** If something isn't in DESIGN.md or the plan, ask or leave a `TODO(design):` note.
9. **Never push to `main` or `master`.** Work on a branch, push the branch and open a pull request. CI (`checks (Python 3.11)` and
   `checks (Python 3.13)`) must be green before merging. A `pre-push` hook blocks direct pushes locally.

## Gotchas (learned in the spike, don't rediscover them)
- **Metric/alias names**: lowercase letters, digits and `_`, at least 2 characters, no `__`. `alias: v` fails parsing.
- **Schemas**: without the custom `generate_schema_name` macro, dbt-duckdb creates `main_snapshots`, `main_finance` and so on. Implement the macro in Phase 0 so schemas are exactly `raw, staging, intermediate, snapshots, core, finance, operations, growth, risk, audit`.
- **Snapshots** need their source model built first (`dbt run -s <model>` before `dbt snapshot`). `dbt build` handles the order.
- **Telemetry**: set `flags: { send_anonymous_usage_stats: false }` in `dbt_project.yml` and `DO_NOT_TRACK=1` in `run.py`. Outbound calls may be blocked in sandboxes.
- **MetricFlow** reads `target/semantic_manifest.json`. Run `dbt parse`/`build` first, and run `mf` inside `dbt/` with `DBT_PROFILES_DIR` set.
- **`mf query --explain`** prints a header line (`🔎 SQL (...)`) before the SQL. Strip everything up to the first blank line after it. Keep that logic in one helper.
- **Period-over-period metrics** must be queried with `metric_time` in the group-by. Saved-query output isn't ordered, so add `order_by` or sort in pandas.
- **DuckDB locking**: one writer OR many readers. The dashboard must use short-lived `duckdb.connect(path, read_only=True)` connections and never call `mf` at runtime (it executes compiled SQL instead).
- Verified in Phase 6: measure-level `agg_time_dimension`, `validity_params` on the SCD2 `dim_users` semantic model (needs `primary_entity: user` with a `natural` entity; validity is resolved at day granularity) and `non_additive_dimension` (a quarter shows its last month).
- Saved-query `order_by` descending must be written `"Metric('x').descending(True)"`, not `"-x"`.
- Offset metrics (`offset_window: 1 year`) also emit the 12 months after the data ends, and succeeded-dated measures produce a NULL `metric_time` bucket. Saved queries filter `metric_time is not null`; readers trim trailing empty months (presentation only).
- `mf` opens DuckDB read-write: never keep a DuckDB connection open (even read-only) while `mf` runs.

## Conventions
- **Naming**: `stg_felix_backend__<entity>`, `int_<entity>__<verb>`, `fct_` / `dim_` / `bridge_`, `snp_`. Columns use snake_case, with `_at` for timestamps, `_date` for dates, `is_`/`has_` for booleans, `_usd` / `_local` suffixes for money, and `_sk` for surrogate keys.
- **SQL style**: CTEs (`import → logical → final`), lowercase keywords, trailing commas, one model per file, `select *` only in import CTEs. Must pass `python run.py lint` (sqlfluff for SQL, ruff for Python).
- **Materializations**: staging and intermediate are views. Marts are tables with **enforced contracts**. `fct_payments` and `fct_remittances` are incremental: merge on a load-time watermark (`_loaded_at`, so late or out-of-order rows of any age are picked up) plus a `chargeback_maturity_days` lookback for values that depend on other rows; a load that deletes raw rows triggers `--full-refresh`. `run.py check-incremental` proves incremental = full refresh.
- **Sequence tags**: every model and snapshot has exactly one of `staging`, `intermediate`, `snapshot`, `core`, `marts` (set per folder in `dbt_project.yml`); a new folder needs its tag, or `src/tests/test_run.py` fails.
- **Tests**: every PK is `unique` + `not_null`. Every FK has `relationships`. Every enum has `accepted_values`. Business rules use `dbt_utils.expression_is_true` or singular tests. Source-data problems are `severity: warn`, mart invariants `error`.
- **Money**: `decimal(18,2)` for amounts, `decimal(18,4)` for FX revenue, `decimal(18,6)` for rates.
- **Commits**: small and per task on a branch, e.g. `feat(staging): payments model + tests`, merged through a pull request. Don't commit `warehouse/`, `data/landing/`, `target/`, `logs/`, `dbt_packages/`, `.venv/` or `warehouse/compiled/`.

## How to work each phase
1. Read the phase in `docs/IMPLEMENTATION_PLAN.md` and the referenced DESIGN.md sections.
2. Implement the tasks. Write the YAML (docs and tests) **in the same step** as the SQL, not later.
3. Run the phase's **acceptance checks**. Fix until green. Never weaken a test just to make it pass. If a test reveals a real data issue, handle it in staging or set `severity: warn` with a comment explaining why.
4. Tick the checkboxes in the plan and summarise what changed and anything that differs from DESIGN.md.

## Definition of done (whole project)

CI is green on the pull request, `docs/answers.md` is generated from saved queries, every model and column is documented, `python run.py check-incremental` passes, and `python run.py check-edge-cases` passes (the edge-case batch produces exactly the expected test failures).
